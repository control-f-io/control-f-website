Outside the Page

Every other chapter here is about something a stylesheet draws. This one is about the four declarations that decide what this brand looks like where the stylesheet does not reach — the strip of browser chrome above the page, the scheme the browser is allowed to re-tint it in, and the tile a reader who keeps the site ends up looking at on a home screen. All four are invisible from a desk, and the site shipped one of them.

Where this comes from

The favicon's own file says it. assets/img/logo/cf-favicon.svg opens by arguing the black plate off the tab strip, and the reason it gives is that "a filled near-black square with a rounded corner reads as an app icon rather than as this company's mark". That is right, and it hands the plate somewhere. Nothing was there to catch it.

The manual is the other half. Logo Design > Rahmen defines five frames for the signet — transparent, square, isometric, App-Icon, circle — and the logo chapter costs the web down to two of them: the square frame is the nav plate, the transparent frame is the favicon. The App-Icon is the third the web actually needs, and it is the one frame in the manual that names a surface this repository does not own. It was never drawn.

Counted before this chapter: 138 pages, one browser-surface declaration between them. rel="icon", and nothing else. No scheme, so the page was a light document a browser was free to re-render; no theme colour, so the chrome above a derived wash was the UA's grey; no touch icon and no manifest, so a reader who kept the site got their launcher's thumbnail of a screenshot.

The scheme, and the browser that repaints without asking

Chrome for Android's Auto Dark Theme takes a document that has not declared a colour scheme and re-tints it — background, text, and the images it decides are re-tintable. It is a good feature and it is aimed at pages that never thought about the question. This site's every colour is derived: --wash-stops opens at #CFCFD2 and lands on white, the ramps are checked against the OKLab path, and thirteen contrast ratios are recomputed from the tokens on every run. None of that survives an automatic inversion, and none of it can see one.

This is the failure mode no measurement in this repository could reach. A desktop browser ignores the feature outright, so the responsive sweep at 375 / 768 / 1280 / 1920, every screenshot under docs/, the contrast register and the runtime console all agree the page is fine. It is visible only to somebody holding an Android phone with the setting on, and that person is not in the review — the same shape of gap Mobile found in the viewport directive.

The opt-out is the only keyword, and it is also the honest statement: this system has one scheme and this is it. light on its own does not opt out — it names a scheme the page supports and leaves the automatic rendering in place. 

<meta name="color-scheme" content="only light">

html { color-scheme: only light; }

Both, and they do different jobs. The meta is read by the parser before a stylesheet has arrived, which is what stops the darkened first paint; the property is what cascades, which is what lets a subtree say something else. It is also the declaration that decides the surfaces the stylesheets here deliberately leave native — the scrollbar, the form controls Forms keeps as the platform draws them, the spellcheck underline, the canvas behind the page.

And the section that is already dark says so

tokens.css has carried [data-theme="inverse"] since the footer was drawn: Schwarz surface, light ink, light contours, the lattice inverted. It flipped every value this system declares and none of the values the UA declares, so a native control standing inside an inverted section was drawn from the reader's OS preference, on black — a light-mode reader got a white select on a black plate with this system's focus ring around it. 

[data-theme="inverse"] { color-scheme: dark; }

dark and not only dark: the root already forecloses the automatic rendering for the whole document, and repeating only inside it would say this subtree is defending itself against something that cannot reach it.

The colour above the page is a number the page already has

theme-color paints the browser's own bar on a phone, the tab strip on some desktop builds, and the launcher's frame around an installed page. The right value is not a decision: the wash's first stop is what the reader sees at the very top of the document, so the chrome that sits directly above it is that stop and there is no seam.

theme-color · #CFCFD2

--wash-stops, first stop · #CFCFD2

scripts/check-outside-page.py reads that stop out of tokens.css and holds all 138 pages and both manifest colours to it, so the value is derived on every run rather than typed in 139 places. A theme colour written by hand is a second copy of a token that moves.

The tile

The App-Icon frame, drawn at last. Three materials and no more: the opaque layer as the ground, the mark on it, and the light across the mark. An icon has room for exactly one lime moment and this is the whole of it.

The tile is square and the platform rounds it

The manual draws the App-Icon frame with a corner radius, and this system's corner rule allows exactly three rounded things — the logo pill, the nav pill, the avatar. Neither has to give. iOS, Android and every launcher since apply their own mask to a full-bleed square, and a maskable icon is required to be full-bleed with its content inside the centre circle of 80 % diameter. So the artwork keeps the square corner this system draws everything with, the platform draws the manual's radius, and the radius nobody here has to choose is the one the reader's own launcher is already using on every icon standing beside it.

The safe zone is measured, not asserted. check-outside-page.py renders the 512 tile in memory, finds every pixel that is not the ground, and measures the farthest one from the centre: 32.5 % of the tile against a 40 % radius. An icon whose mark crossed that circle would lose a corner of the signet on some launchers and keep it on others, and nothing else in this repository — nor any screenshot taken on the machine that built it — would show which.

Why the ramp ends at Weiss and not at CF-Grau

Every ramp in the light family falls off to the ground it stands on, and on the page that ground is CF-Grau. Here it is Schwarz, and a mark that falls off to its own ground disappears — the far end of this ramp has to stay a mark. Weiss is where the falloff stops instead: the same leg, ending at the brightest thing the palette has rather than at the dimmest. The mark is not painted lime. It is painted white and lit, which is the distinction the light chapter is about.

The waypoint at 19 % of the lime leg is the family's one convention for a ramp written as stops — it is what makes an sRGB gradient track the OKLab path the family is defined on — and 0.0855 of 0.45 is that ratio. Every rung clears the 3:1 floor a graphical object needs, at both ends of the ramp and everywhere between them, so the mark is legible whatever slice of the ramp a launcher's mask leaves standing.

The manifest, and why it is generated

It exists for the icon and the two colours, not to be installed: display is browser, because taking the address bar away from a reader who did not ask for an app is not this system's decision to make. 

<link rel="apple-touch-icon" href="../assets/icon/cf-app-icon-180.png">
<link rel="manifest" href="../assets/icon/site.webmanifest">
Every address in it is relative, and that is a deploy fact rather than a style. There is no CNAME on the Pages deploy, so the document root is /control-f-website/ there and / on Cloudflare. A manifest whose start_url named either would be right on one host and silently wrong on the other — the same finding the links check was written for. The manifest sits three levels below the site root on both, so "../../../" is the root on both.

Its two colours are read out of tokens.css by scripts/build-app-icons.py on every run, and the tiles are rendered by the same script out of the signet and the ramp above — the stdlib rasteriser the share plates already own. No dependency, no second drawing of the mark, and nothing committed: .gitignore keeps the output out for the reason it keeps the plates out, and --check re-renders and compares bytes so a tile edited by hand fails rather than being rebuilt over.

Accessibility

only light forecloses an automatic dark rendering, and it is worth being clear about who that costs. A reader who prefers dark interfaces gets a light page here. The alternative on offer is not a designed dark page — it is an algorithm's guess at one, applied to a wash, four gradient families and a lime light layer that were each derived against a specific ground, with no contrast guarantee at the far end of it. A guess that lands at 3:1 on body copy is worse for that reader than a light page that measures.

So the keyword is a promise as well as an opt-out. The day this system wants a night, it draws one: [data-theme="inverse"] is most of a dark palette already, the wallpaper ships a dark plate beside its light one, and the manual's own colour-application plate composes on Schwarz. What only forbids is shipping somebody else's.

The tile carries no text and states no meaning that its alt has to repeat — an apple-touch-icon is named by the manifest's name and by the page title, which is where a screen reader on a home screen reads it. Both are "Control-F".

Rules

Do

  • Declare the scheme in both places. The meta stops the first paint, the property cascades, and a page with one of them has half the rule.
  • Take the theme colour from the wash. It is the pixel directly under the chrome, so the seam is the test and there is only one right answer.
  • Give a section that inverts the tokens a color-scheme too. Anything the UA draws inside it is otherwise drawn from a preference this page has already overruled.
  • Keep the tile full-bleed and square, and keep the mark inside the 80 % circle. The platform's mask is the manual's radius, drawn by the reader's own launcher.
  • Render the icon from the signet and the ramp, never redraw it. A second drawing of this mark is a second answer to what it is.

Don't

  • Never content="light" on its own. It names a scheme and does not opt out, which is the failure this whole chapter is about wearing the look of the fix.
  • No rounded corner in the artwork. A radius baked into the tile is masked again by the launcher and comes back as a thinner, wrong one.
  • Do not paint the mark lime. Lime is the light on it; a lime letterform is a lime surface, and this system has one of those and it is not this.
  • Never write a hex into the manifest or into a theme-color. It is a token, it moves, and 139 hand-written copies of it move on 139 different days.
  • Do not add sizes because a generator offers them. Every extra raster is another file that can go stale alone, and a launcher downsamples better than this rasteriser would.
  • Never display: standalone to make the site feel like an app. It takes the address bar from a reader who asked for a website.
