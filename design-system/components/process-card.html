The sequence

Four cards, four objects, one story from first contact to running operations.

The objects get more concrete from front to back: card 01 is an excavation with nothing in it yet, card 04 a system in motion. Only one element per object carries the lime gradient, and it is always the one the eye should land on.

Figma reference

The original exports, for checking proportions and how the objects are constructed:

The four objects are now built from the designer's source vectors (assets/source/illustrations/), not approximated. Geometry, gradient stops and construction points are the exported ones; three things were changed on purpose, each because the export broke a rule the system does hold:
  • Lime is #E1FF00, not the export's #E0FF02.
  • Dash patterns 8-2, 2-8 and 2-2 were mapped onto the four sanctioned line types (2-1, 1-4, 1-2). See Geometry.
  • Card 02 carried lime in two of its three plates. The dominant one — the right-hand rim — keeps it; the middle core drops to Glas, so each object has exactly one lime moment.
Card 04's tangent was also trued from 26.96° to exactly 26.57°, and Figma's inner-shadow bevel on card 03 was dropped: it is not one of the six material layers.

That is now a checked claim rather than a stated one. scripts/check-illustration-source.py matches every geometry element of every shipped process object — 326 of them, across the four cards, the English edition and the prototype — against its source vector, tag, coordinates and transform, at the two decimals the exports are written to. The four deviations above are the only ones it allows, and three of the four are re-derived rather than listed: a dropped transform has to be provably a no-op, the split traces have to partition the source path exactly, and the trued angle has to be exactly 2:1 where the source was not. Colour is not its business — check-gradient-family.py owns the waypoint and check-paint-register.py the literals.

A rotation that looks redundant and is not

Card 04's three orbits are dashed 1-4 ellipses stroked with a gradient, not a flat black — each one is solid along part of its length and fades to nothing along the rest, which is what stops three full rings reading as a wire ball. All three carry a rotation in the source vector. Two of them are 2:1 ellipses, where the rotation is obviously load-bearing. The third is a true circle, and its rotate(-90 403 513) had been dropped as a no-op.

It is not a no-op. The gradient is gradientUnits="userSpaceOnUse", and a paint server is resolved in the user space in force where it is referenced — which includes the element's own transform. Rotating the element rotates its paint with it. The geometry of a circle is unchanged by a spin about its own centre; the direction its stroke fades is not.

Measured on the landing page itself, at the shipped 352 px render: darkest stroke ink found on a short arc at each cardinal point of the ring, 0 = nothing there, 255 = solid black. The arc is scanned rather than a single pixel sampled because the ring is dashed 1-4, so most exact points fall in a gap.

One quadrant is empty in each case, and it is a different quadrant: the fade axis was 90° out. The designer's orbit is solid on the left and dissolves to the right, away from the trace that arrives from the lower left. The shipped one dissolved downwards instead, which spent its solid half across the top of the lime disc — the one place on the object the eye is meant to land. Restored to the source verbatim, so a diff against assets/source/illustrations/ now shows no drift on this object — and that diff is run on every push rather than asserted here: dropping this rotate(-90) again fails scripts/check-illustration-source.py, while dropping the identical attribute from the eight flat-filled dots beside it still passes. Same attribute, same shape, different consequence — as a rule the script re-derives rather than a pair of names it was given.

The general rule: never drop a transform from an element that is painted with a userSpaceOnUse gradient, however redundant it looks against the geometry. The eight construction dots on the same object carry the identical rotate(-90) and are flat-filled black — dropping it there was correct, and is why the orbit's was dropped too. Same attribute, same shape, different consequence.

The same fact read forwards decided how these three rings are animated. They now turn as the object assembles — they are the only geometry in the system drawn as motion, and they used to be the only thing on the page that said “this is circulating” and then held still. They do not turn by taking an animated rotation, because that would drag the fade round with them and re-create, once per scroll, exactly the defect the table above measures. They turn by travelling their dashes, which touches no paint server: the ring does not swing, the things on it go round. → Motion > An orbit turns

And they are this object's plan, so they are the first thing on screen. A built object draws its dashed geometry first and the solids arrive into it; card 04's three orbits are the only dashed geometry it has, so for one release that window ran empty and the rings faded up over a finished sphere — measured at 375 px, first orbit ink at cover 20 % with the eleven forms already at mean opacity 0.444. They now open with the plan at 2 % and turn until the construction points settle at 50, which is the whole assembly rather than its second half. The settled ring is unchanged: same 60 px of travel, same twelve dashes, same phase. → Motion > It turns while the object assembles

Card 03's arrow is five traces, not one path

The source vector draws the incoming signal as a single <path> with five subpaths — a shaft, an arrowhead's two barbs and two speed chevrons trailing behind it — and the shipped copy inherited that shape. It is the wrong shape for a line that draws itself. A dash pattern restarts at every subpath while pathLength normalises the path as a whole, so each of the five drew its own first 1 − offset of the total, all at once, and the arrow was finished as soon as the longest of them was: the shaft is 0.3265 of 344.61 units, so the whole drawing was complete at stroke-dashoffset 0.6735 — cover 26.8 % of a range running to 45 %. Two thirds of its scroll range was spent on a picture that had stopped changing, and what the range it did use showed was five strokes sprouting from five points rather than a signal arriving.

It is five traces now, on three leads — the far chevron, then the near one, then the arrowhead and the shaft together — so the signal travels left to right into the disc, in the direction the designer drew it flying. The settled drawing is unchanged to the coordinate: same five strokes, same round caps, same places. One d is written backwards from the source (M300 511.5H412.5 for M412.5 511.5H300) because a stroke's direction is invisible at rest and is the whole of the draw. → Motion > A trace is one stroke

Behaviour

  • From a 56rem container: two equal columns, and the panel grows with its text. Square is the figure’s minimum, not its height — the drawing inside is capped at 22rem and centred, so past the square a taller figure is more air around the same object. It has to grow, because in this form the figure’s right border is the card’s divider: left at its square it stops 49 px above the card’s bottom edge at 1440 on the landing page’s third card, and 140 px at 1280. → scripts/check-figure-letterbox.py
  • Below that: stacked, the figure at 4 : 3 and capped at the drawing's own 22rem plus its padding, panel padding down to 24 px. The fold is a container query, not a viewport one — on this page the component folds at a 901 px viewport, because the sidebar is in the way.
  • In the design the four cards swap on scroll. The landing page does that without scroll hijacking: from 64rem wide and 45rem tall, with motion allowed and scroll-driven animations supported, the section pins one lectern and scrubs the four builds off the track's timeline. Everywhere else — narrower, shorter, reduced motion, no support — the four cards stack, each with its own counter, and each object builds on its own view timeline as it crosses the viewport. → Motion > A pinned track
  • All four must be readable without JavaScript — the sequence is content, not interaction.

Accessibility

This card has no keyboard contract, and that is a property of it rather than an omission. All seventeen instances in the tree were walked for a descendant <a>, <button>, <input>, <select> or <textarea>, and there are none. Nothing here takes focus, nothing here has a hover response, and nothing here is a control wearing the clothes of one. It is four paragraphs and a drawing.

  • The figure is aria-hidden="true", on all fourteen of them. The object is the panel's sentence drawn a second way; it carries no fact the copy beside it does not carry in words. An <svg> left in the tree with no role and no name buys the reader an unnamed graphic, which is noise — so it is removed from the tree rather than titled. The counter-case is real and is somebody else's component: an object whose content is the information — the plot, the pie, the Gantt — takes role="img" and a name, and those chapters do exactly that.
  • The title is an <h3>, on every shipped card — four on the landing page, four on its English edition, four in the prototype, two here — under the <h2> that names the section. That is what makes the sequence navigable: a reader moving by heading gets Service Offering and then the four steps under it, in order, whether the cards are pinned or stacked. Nothing else in the panel is a heading. The subtitle and the benefit label are mono labels on a <p>, and promoting either would put a second heading level inside one card for a line that is not a section of anything.
  • The counter above the sequence is announced or hidden by which of the four forms it takes, not by where it sits. On this page it is a position — 01 / 04, aria-hidden, because on a single specimen it says nothing a reader cannot see. On the landing page it is a quantity — 4 Schritte — and is left in the tree, because the number of steps is a fact about the section. → Section Header
  • Contrast. The panel's ink is --text-secondary, which check-contrast.py recomputes at 5.88 : 1 against the worst point of the page wash — the floor for 14 px prose is 4.5. In the two-column form the panel additionally carries --surface-lifted, 26 % white over that same wash, so the ratio there can only rise. The mono labels are 11 px and are held to the same 4.5 rather than to the large-text 3.0.
  • Reduced motion costs the reader nothing. The build is a scroll-driven animation over geometry that is already in the document; under prefers-reduced-motion: reduce the pinned track is not taken, the four cards stack, and every object stands finished. check-runtime.py drives every pattern page under reduce and reports nothing running — the settled drawing is the same drawing.
  • It survives the reader's own type size. The card's one fold is a container query stated in rem, so a root of 20 or 24 px moves it with the text instead of leaving four paragraphs in a column sized for 16 — and the drawing's cap, its padding and the figure's height cap are all rem too, so the object grows with them. scripts/check-text-zoom.py holds the pattern pages the component ships on.

Do & don't

Do

  • Give the object exactly one lime element, and make it the one the eye should land on. Four cards, four lights, one each.
  • Build the object from the designer's vector in assets/source/illustrations/, coordinate for coordinate. check-illustration-source.py matches 326 elements against those files and allows four named deviations.
  • Keep the title an <h3> under the section's <h2>, so the four steps are four headings in order.
  • Put the note last. It is pinned to the foot of the panel, so anything after it in source order lands above it on screen.
  • Let the copy set the card's height and the drawing keep its size. Past the square the figure half is more air around the same object, never a bigger one.
  • Wrap the set in a <section> named by the section header's heading, and let the header's counter say how many steps there are.

Don't

  • Don't put a link or a button in the card. The step is the content; a card that is four paragraphs and one control reads as a control, and this component has no drawing for a focus ring.
  • Don't give the figure a role or a name. It is the panel's sentence drawn again, and naming it makes every card read twice.
  • Don't drop a transform from an element painted with a userSpaceOnUse gradient, however redundant it looks. → A rotation that looks redundant and is not
  • Don't fill the card. It is a contour; the only surfaces in it are the note's veil and, beside the copy, the two-column form's light plate.
  • Don't draw the sequence as one path with several subpaths when it has to draw itself. A dash pattern restarts at every subpath and pathLength does not. → Card 03's arrow is five traces
  • Don't fold the card on a viewport query. The fold is about how wide the card is, and on this page a 901 px viewport leaves it 533.
  • Don't make a step depend on the scroll. All four have to be readable with the animation never running.
